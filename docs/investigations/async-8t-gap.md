# 调查：8 线程异步闭环只有同步的 80%–93%

> 状态：调查完成（2026-10-20）；建议 1 已实施，见文末“后续”。来源：[roadmap](../roadmap.md)“6.4 之后”的待调查项；背景见 [RFC 0004](../rfc/0004-async-api.md) §14“6.3 / PR 2”。

## 结论摘要

- **主因：异步链每一级都派发一次。** `handleNext` / `thenNext`（`core/.../internal/Futures.kt`）只在**登记时**前驱已经完成才就地执行。引擎的异步链是在 L1 应答到达之前一次装配好的，所以登记时每一级都没完成，完成时每一级都 `executor.execute` 一次——**包括前驱已经在异步执行器上完成的那些级**。实测每次操作的派发次数：

  | 路径 | 实测派发次数 / 操作 | A9 要求的次数 | 多出的次数 |
  |------|------|------|------|
  | `l1HitViaEngineAsync`（L1 命中） | 4.0 | 1（L1 应答之后） | 3 |
  | `missLoadAsync`（同步 loader） | 7.0 + 1 次阻塞执行器 | 3（L1 读、loader、fill 之后） | 4 |
  | `setAsync` / `invalidateAsync` | 1.0 | 1 | 0 |

  8 线程差距的大小与“多出的派发”同序：写入约 93%，L1 命中约 87%，未命中约 81%。

- **代价在 ForkJoinPool 的唤醒上，不在派发本身。** 默认执行器是并行度为 CPU 数（本机 10）的 `ForkJoinPool`。从工作线程提交任务会 `signalWork`，唤醒一个空闲的工作线程；闭环负载下工作线程大多空闲，于是每一次多余的派发都是一次 park / unpark。JFR 显示：默认池的 `cocache-async-*` 线程 CPU 中 **76% 是内核态**，为同样的工作耗费的 CPU 约为并行度 2 时的 4 倍。
- **对照实验印证了这两点**：续接就地执行（`direct`，违反 A9，只作上界）在 1 线程下为同步的 102%，在 8 线程下为 93%–104%。并行度 2 的 `ForkJoinPool`（`fjp2`）在 8 线程下比默认池快（L1 命中 8 个同轮配对中 7 个更快，中位 +12%；未命中 3 对 +7%~+18%）。单纯的“一次切换”（存储层读 + 一次 `thenApplyAsync`）在 1 线程下只花 1%–3%。
- **有不碰不变量的低成本修复**（建议 1）：前驱已在异步执行器的续接里完成时就地执行，不再派发。预计 L1 命中从 4 次派发降到 1 次，未命中从 7 次降到 3 次。8 线程 L1 命中预计回到约 93%（同样只派发 1 次的 `setAsync` 的水平），1 线程回到 97%–99%。**按任务要求未实施，等待决定。**

## 方法

- **环境**：Apple Silicon，10 核（4 性能核 + 6 能效核），macOS；OpenJDK 17.0.20.1（Homebrew），JMH 经 `cocache-redis` 的 `jmhJar` 直接运行；Redis 7（Docker，`localhost:6379`），单机自建客户端（`CommandTimeouts.CLIENT`，即 #667 之后的计时方式）。
- **背景负载**：开跑前负载约 4。另有一个与本组会话无关的外部 JVM 全程占满一个核，运行中负载在 3–10 之间。**绝对吞吐因此偏低、波动大，只有同轮配对比值可信**；JFR 热点不受影响。jmh-compare 会话在 23:17:02–23:17:45 跑过一次 Gradle 构建，与它重叠的第 1 轮 `l1ReadAsync` / `l1ReadAsyncHop` 1 线程运行已作废。
- **诊断基准**（不提交，源码与原始数据放在协调会话的共享笔记 `async-8t-gap/` 中）：`AsyncGapBenchmark`，与 `CoCacheBenchmark` 相同的缓存配置，用 `@Param executor` 换运行时的执行器：
  - `default`：运行时默认（`ForkJoinPool`，并行度 = CPU 数，asyncMode）。
  - `direct`：异步执行器与阻塞执行器都就地执行（续接会在 Lettuce I/O 线程上执行，**违反 A9**，只用来量出“所有切换”的上界）。
  - `fjp2`：并行度 2 的 `ForkJoinPool`。
  - `count`：包装默认池，统计每次操作的派发次数。
  - 另有 `l1ReadAsyncHop`：存储层 `readAsync` 之后恰好一次 `thenApplyAsync` 到池上，隔离“一次切换”的代价。
- **运行方式**：每个基准单独一个 JMH 进程（`-f 1 -wi 2 -w 3s -i 4 -r 4s -prof gc`），同一轮内各变体交替，偶数轮倒序。作废规则：迭代间 CV > 3%（8 线程另列 CV ≤ 5% 的结果），或运行中负载上升超过自身贡献（线程数 + 1）+ 1.5。主要结论用**同轮配对比值**。
- **剖析**：JFR（JDK 自带，`-XX:StartFlightRecording`，以 `profile.jfc` 为底，执行采样 1 ms、`ThreadCPULoad` 1 s、分配采样 3000/s），8 线程，`l1HitViaEngine`、`l1HitViaEngineAsync`（`default` 与 `fjp2`）各录 14 s，用 `jfr print --json` 汇总。

## 热点

### 时间花在哪里：线程 CPU（JFR `jdk.ThreadCPULoad`，8 线程，相对值）

| 线程组 | 同步 | 异步 `default` | 异步 `fjp2` |
|------|------|------|------|
| JMH 调用方线程 | 0.34（用户 0.14 / 内核 0.20） | 0.21 | 0.19 |
| Lettuce I/O | 0.28 | 0.22 | 0.22 |
| 异步执行器 | — | **0.54（用户 0.13 / 内核 0.41）** | 0.14（用户 0.06 / 内核 0.08） |
| Caffeine 维护（`commonPool`） | 0.10 | 0.07 | 0.06 |

- 默认池的工作线程以内核态为主（76%），执行采样里几乎看不到它们（14 s 只有 6 个 Java 栈样本：`topLevelExec`、`awaitWork → park`、`signalWork → unpark`）。也就是说，它们的 CPU 几乎都花在 park / unpark 的系统调用上，而不是续接本身（解码、填充 L2 只占很少）。
- 并行度 2 时同样的工作只需约四分之一的 CPU：空闲的工作线程少，提交时需要唤醒的次数少，任务多由已经醒着的线程顺手执行。
- JFR 的执行采样在 macOS 上很稀疏（每个线程组几十个样本），只用来定性；定量结论来自上面的 JMH 配对与派发计数。

### 分配

异步 L1 命中比同步多约 2 KB/op，按 JFR 分配采样的权重，多出的主要是 `CompletableFuture`（15.7%）、`UniWhenComplete`（6.3%）、续接 lambda（合计约 9%）、`Futures.outcome` 的 `Pair`（2.5%）；分配点集中在 `handleNext`（12.9%）、`Futures.relay`（6.2%）、`SingleFlight.executeAsync`、`AsyncView.toUser`。`direct` 的分配与 `default` 几乎相同，吞吐却回到同步水平，所以**分配不是差距的来源**（每秒约 60–150 MB，对 GC 无压力）。

### 派发是怎么多出来的（L1 命中）

`AsyncView.get` → `loadMissAsync` → `SingleFlight.executeAsync { loadThroughAsync }`，在调用方线程上一次装配：

1. `readWaitingLeaseAsync`：`readAsync(...).thenNext(executor)`——L1 应答在 I/O 线程上到达，**派发 1**（A9 要求）。
2. `loadThroughAsync`：`readWaitingLeaseAsync(...).handleNext(executor) { onHitAsync … }`——登记时前驱未完成；前驱在步骤 1 的工作线程上完成，**派发 2**。
3. `entry.thenNext(executor) { Loaded(it, stamp) }`——同理，**派发 3**。
4. `loadMissAsync` 的 `flights.executeAsync(...).thenNext(executor) { loaded -> … }`——同理，**派发 4**。

派发 2–4 的前驱都在异步执行器的线程上完成，切换不带来任何隔离，只带来一次 `ForkJoinPool` 提交与（大概率）一次唤醒。未命中路径另有 `loadAndFillAsync`、`timedAsync`、`fillAndComplete`、读己之写重试等几级，同样如此。写入路径（`AbstractEngine.writeAsync`）只在 L1 完成时派发一次，所以几乎没有多余开销，它剩下的 8 线程 6%–8% 是 A9 要求的那一次切换本身。

## 结论

| 来源 | 占比估计（8 线程 L1 命中，约 13 个百分点的差距） | 依据 |
|------|------|------|
| 多余的派发（前驱已在执行器上完成仍再派发）引起的 `ForkJoinPool` park / unpark | **一半以上**，约 6–8 个百分点 | 派发计数；只派发 1 次的写入为 93%；`fjp2` 比默认池中位快 12%；默认池工作线程 76% 内核态 |
| A9 要求的一次切换（I/O 线程 → 执行器 → 唤醒调用方） | 约 5–7 个百分点 | `setAsync` 8 线程 93%；`direct` 回到 93%–104% |
| future 分配（多 2 KB/op） | 可忽略 | `direct` 分配相同而吞吐回到同步水平 |
| `orTimeout` | 0 | #667 已排除 |
| 锁 / CAS 争用 | 未见 | 异步录制中 `JavaMonitorEnter` 为 0（阈值 10 ms）；执行采样中没有锁或 CAS 自旋热点 |

1 线程下的 9% 差距同样主要来自多余派发：只派发一次的 `setAsync` 与“存储层 + 一次切换”都只差 1%–3%。

## 建议

| # | 建议 | 是否触及不变量 | 预估收益 | 成本 |
|---|------|------|------|------|
| 1 | **前驱已在执行器的续接中完成时就地执行**：`Futures.dispatch` 执行任务时在线程局部变量上做标记；`handleNext` 的 `whenComplete` 回调发现当前线程正处在本引擎派发的续接中时直接执行，不再 `execute`。I/O 线程、定时器线程、用户 loader 的线程上没有标记，仍然派发 | **不触及**。A9 只要求续接不在 I/O 线程上执行；就地执行的线程本来就是异步执行器的线程。`SingleFlight` 先注销再发布的顺序、执行器拒绝时的释放路径不变（被拒的只会更少） | L1 命中 4 → 1 次派发，未命中 7 → 3 次。预计 8 线程 L1 命中由约 87% 到约 93%（写入的水平），未命中由约 80% 到约 88%；1 线程到 97%–99%；同时省下默认池约四分之三的 CPU | 低：改 `Futures.kt` 一处（一个 `ThreadLocal` 标记，或判断当前线程是否 `ForkJoinWorkerThread` 且属于该池——后者对用户提供的执行器无效，前者通用）。需要补测试：续接仍不在 I/O 线程上（已有 TCK 覆盖）、嵌套深度有界、拒绝路径。命中路径（L2 命中）不经过这里，不受影响 |
| 2 | 链的装配改为“完成后再装配下一级”（例如 `loadThroughAsync` 不在 I/O 之前挂好后续阶段） | 不触及 | 与建议 1 相同 | 中：改写多处异步链，审阅面大；建议 1 一处修改就能得到同样效果，不推荐 |
| 3 | 默认异步执行器的并行度从 CPU 数降到较小值（如 `min(4, CPU)`） | 不触及（执行器仍是运行时自建的池） | 在建议 1 之后剩余的收益未测；单独使用时 8 线程中位 +12%（本机） | 低，但有风险：用户续接若阻塞，小池更易饿死（`ForkJoinPool` 的补偿只对 `join` / `ManagedBlocker` 生效）。依赖机器与负载，建议在建议 1 之后再测，不默认改动 |
| 4 | 减少中间 future（`relay`、`Pair`、`completed(...)`） | 不触及 | 吞吐上可忽略（见“分配”），GC 压力略降 | 中，收益不足以单独立项 |
| 5 | 阻塞等待的调用方（`join()`）由等待线程自己执行最后一步续接 | 不触及 A9，但要自定义返回给用户的 future 类型 | 理论上可再省掉 A9 那一次唤醒中的一部分 | 高；闭环阻塞本应使用同步 API，不推荐 |

**下一步需要决定**：是否实施建议 1。若实施，验收用本报告的方法：`CoCacheBenchmark` 的 `l1HitViaEngineAsync`、`missLoadAsync`、`setAsync`、`invalidateAsync` 与同步对照，1 与 8 线程，每侧至少 5 轮交替，按同轮配对比值判断；另确认 `l2HitAsync` 不变（命中路径不经过 `handleNext`）。

## 后续：建议 1 已实施

维护者批准后实施了建议 1（PR `perf/inline-continuations`）：

- `Futures.dispatch` 派发的任务执行期间，以线程局部变量把当前线程标记为该执行器的续接；`handleNext` / `thenNext` 的完成回调经 `Futures.continueOn`：当前线程带有同一执行器的标记且嵌套不超过 16 层（`MAX_INLINE_DEPTH`）时就地执行，否则照旧派发（新任务从第 0 层开始）。标记在 `finally` 中恢复。
- I/O 线程、定时器线程、阻塞执行器与数据源自己的线程上没有标记，在那里完成的结果仍然派发，A9 不变。执行器拒绝时的释放、写入收尾、非原子广播的就地广播、`SingleFlight` 先注销再发布的顺序都不变；返回给用户的 future 仍在异步执行器上完成，用户注册的非异步回调执行的线程与此前相同。
- 测试：`AsyncDispatchTest` 用计数执行器与在另一线程送达 L1 结果的后端断言 L1 命中每次 1 次、未命中至多 3 次、写入 1 次、L2 命中 0 次（改动前分别为 4 次与 4–5 次）；`FuturesTest` 覆盖同执行器就地、不同执行器派发、深度上界与异常后恢复标记。
