# 8.0 GA 性能对比：v6.10.0 → 8.0 代码冻结点

> 状态：完成（2026-11-04）；GA 前的架构审查之后复测（2026-11-07，见“GA 前复测”），预算仍全部满足。结论：**RFC 0005 §7 的预算全部满足**，含 GA 前补测的一行（权威缓存的 `Absent` 与外部来源的“未填充”）。声明的挂起视图接口的代理每次命中多约 10 ns（见“补测”），原因是 C2 的内联深度上限；读取改经方法句柄转发之后修复，见文末“后续”。来源：[RFC 0005](../rfc/0005-v8-target-architecture.md) §7 的预算表；[todo](../todo.md) §0“JMH 延后到 GA 前”（维护者，2026-11-03：开发期间各切片不跑，GA 之前对 v6.10.0 做一次对比）。

## 结论

| RFC 0005 §7 的行 | 基准 | 线程 | 预算 | 结果（new/base 同轮比值的中位数） | 判定 |
|------|------|-----:|------|------|------|
| L2 命中 | `l2Hit`、`l2HitViaInterface`、`l2HitMixed`、`l2HitAsync` | 1、8 | 不退化 | 109.5%–254.4% | 满足 |
| L1 命中、未命中回源（同步变体，含 `runBlocking`） | `l1HitViaEngine` | 1、8 | 退化 ≤ 3% | 98.2%、98.7% | 满足 |
| 同上 | `missLoad` | 1、8 | 退化 ≤ 3% | 97.8%、98.9%（默认设置复测） | 满足 |
| 异步视图的 L1 命中、未命中 | `l1HitViaEngineAsync`、`missLoadAsync` | 8 | 不低于 6.10 的 90% | 96.4%、96.2%（默认设置复测） | 满足 |
| L2 填充（`compute` + 条件复核） | `missLoad` | 1、8 | 未命中路径退化 ≤ 2%（这一项改动单独的增量） | 99.9%、99.3%（#721 对 #720） | 满足（在 M2a 测得，见下） |
| 条件读取（摘要未变） | `conditionalUnchanged` | 1、8 | Redis 端成本与载荷大小无关 | 1 KB → 8 MB 吞吐变化 ≤ 4.6%（在误差内） | 满足 |
| `Store` 的 L1 读取 | `authoritativeL1Read` | 1、8 | 成本只在 L1 读取上，L2 命中不变 | 绝对值见下；L2 命中由上面的 L2 行覆盖 | 满足 |
| 权威缓存的 `Absent` 与外部来源的“未填充”进入 L2 | `l2HitAbsent`、`l2HitUnfilled` 对 `l2Hit`（补测） | 1、8 | 命中成本与普通 L2 命中相同（在噪声之内） | 97.3%–98.7%（每次命中多约 0.1 ns） | 满足（在噪声之内，见“补测”） |

**`missLoad` 对应两行，判定按第 2 行**：
- 第 2 行（同步变体的 L1 命中与未命中回源，≤ 3%）是 8.0 相对 6.10 的累计预算，包含协程核心、`runBlocking`、L2 填充等全部改动。本次对比测的就是这个累计值：1 线程退化 2.2%，8 线程 1.1%，都在 3% 之内。
- 第 5 行（L2 填充的 `compute` + 条件复核，≤ 2%）是 M2a 这一项改动单独的增量，在 #721 中对它的前一个提交（#720）测得：`missLoad` 1 线程 99.9% [99.5%–100.7%]，8 线程 99.3% [96.0%–101.4%]。用 8.0 对 6.10 的累计值去套这一行会把其它切片的成本也算进来。
- 1 线程的 2.2% 即使按 2% 看，超出的 0.2 个百分点也在同机运行之间的波动之内（architecture.md §14）。

**附带测量（无预算）**：`set` 1 线程 95.8%（默认设置复测），8 线程 98.3%。

## 方法

按 [architecture.md](../architecture.md) §14 与 `scripts/jmh-compare.sh`：
- 每次 JMH 只跑一个基准；同轮两侧交替，先后逐轮轮换；结论看同轮配对比值 new/base 的中位数与 [min–max]。
- **筛查**：`-r 3 --warmup-iterations 2 --warmup-time 2s --iterations 3 --time 3s`，1 与 8 线程（异步视图只跑 8 线程，预算按 8 线程定义，RFC 0004 §11 的口径）。
- **复测**：筛查之后，离预算不到 1 个百分点、或有效配对少于 3 的格子按默认设置复测（5 轮，预热 3 × 3 s，测量 5 × 5 s），以复测为准。复测的格子：`missLoad` 1 与 8 线程（离 2% 不到 1 个百分点，当时按第 5 行判断，见上）、`set` 1 线程（2/3 有效配对）、`l1HitViaEngineAsync` 与 `missLoadAsync` 8 线程（各 2/3 有效配对）。
- 两侧的基准代码对这些方法逐字相同，只有 `l2HitViaInterface` 的构造不同：6.10 把同一个引擎包进代理，8.0 经 `CoCacheFactory` 建一个配置相同的引擎；命中路径多出的都只是代理的转发。

### 没有对应基准的行

- **跟随者**（10 000 个异步调用等待同一次加载时不创建线程）：是用例，不是 JMH。
- **权威缓存的 `Absent` 与外部来源的“未填充”进入 L2**：对比时 `l2HitAbsent` 在两侧都不存在；#785 加入它与 `l2HitUnfilled` 之后在 GA 前补测，见“补测”。
- **`l1Read`**：RFC 把它列在 L2 填充一行，但它直接读 `RedisL1Store`，不经 L2；L2 填充的成本由 `missLoad` 承担（第 5 行的增量已在 #721 测得）。
- **`l1BatchViaEngine`**：只有 8.0 有，只记绝对值（见下）。
- **内存**：是 `MEMORY USAGE` 的对照，不是 JMH，本次不在范围内。

## 补测：`Absent`、未填充与声明的视图接口（2026-11-04）

上面的对比之后，#785 加入了 RFC 0005 §7 列出的 `l2HitAbsent`（权威缓存的 `Absent` 在 L2 中）与 `l2HitUnfilled`（外部来源的“未填充”在 L2 中），#789 让声明的缓存接口可以继承挂起与异步视图（经 `ViewHandler` 转发）。本 PR 在 `CoCacheBenchmark` 中加入三个基准，与被比较的基准同类、同后端、同一种发起方式：
- `l2HitViaSuspendingInterface`、`l2HitViaAsyncInterface`：经声明的挂起与异步视图接口，放在 `l2HitViaInterface` 旁。
- `l2HitSuspending`：不经代理的挂起视图，作为挂起接口的参照，引擎的配置与挂起接口相同。

两个挂起基准都经 `startCoroutineUninterceptedOrReturn` 发起，命中时同步返回（命中挂起即失败），测到的是视图与代理，而不是协程的启动。`l2Hit`、`l2HitAbsent`、`l2HitUnfilled` 读同一个 key（`"hot"`，三者是不同的缓存）：L2 按编码后的 key 存取，key 的长度本身就影响命中的成本。

**环境与方法**：
- 新侧是 `main` 的 c34cc648（#789）加上这三个基准；机器与 JVM 同上；Redis 是新建的 `cocache-redis` 容器（`redis:7-alpine`，7.4.12）。第一次运行紧接在 `./gradlew check` 之后，脚本照常等负载降到 7.2 以下。
- 只做筛查（3 轮，预热 2 × 2 s，测量 3 × 3 s），`scripts/jmh-compare.sh` 持有本机的锁，1 与 8 线程：
  1. 两侧都有的基准对 `v8.0.0-alpha.1`：`l2Hit`、`l2HitMixed`、`l2HitViaInterface`（16:54–17:15）。
  2. 只有新侧才有的基准以 `HEAD` 对 `HEAD`（两侧相同，只取绝对值）：`l2HitViaInterface`、`l2HitViaAsyncInterface`（17:15–17:26），以及不经代理的异步视图 `l2HitAsync`（17:28–17:35）。
  3. `HEAD` 对 `HEAD`：`l2Hit`、`l2HitAbsent`、`l2HitUnfilled`、`l2HitSuspending`、`l2HitViaSuspendingInterface`（17:41–17:58）。
  4. 每次分配：`-prof gc`，1 线程，`l2HitSuspending`、`l2HitViaSuspendingInterface`、`l2HitViaInterface` 各一次（同一把锁，17:58）。
- 前三次共 189 次运行，作废 9 次（CV 超过 3%）；第 1 次运行中读另一个 key 的 `l2HitAbsent`、`l2HitUnfilled` 不再采用。
- 基准之间的比值按轮配对：目标基准第 k 轮某一侧的值除以参照基准第 k 轮同一侧的值，每格 6 个比值（3 轮 × 2 侧），取中位数与 [min–max]。脚本逐个基准跑完各轮，所以这是同一次运行中不同时刻的两次测量之比。

`l2HitAbsent` 4.58 ns，`l2HitUnfilled` 4.61 ns。8 线程的吞吐：`l2Hit` 1,496,053,127，`l2HitAbsent` 1,483,206,344，`l2HitUnfilled` 1,467,618,739，`l2HitSuspending` 1,298,573,203，`l2HitViaSuspendingInterface` 436,787,243，`l2HitViaInterface` 972,517,633，`l2HitViaAsyncInterface` 1,025,696,158，`l2HitAsync` 1,223,601,332 ops/s。

**每次分配**（`-prof gc`，1 线程，`gc.alloc.rate.norm`）：`l2HitSuspending` 0 B/op，`l2HitViaSuspendingInterface` 0 B/op，`l2HitViaInterface` 24 B/op。

**判定**：
- **权威缓存的 `Absent` 与外部来源的“未填充”（RFC 0005 §7）：满足。** 两者是普通 L2 命中的 97.3%–98.7%，每次多 0.1 ns 左右，在噪声之内（8 线程的同机波动约 ±4%，architecture.md §14）。读不同长度的 key 时测得的 5%–6% 差距来自 key 的长度，不来自 `Absent` 或“未填充”。
- **声明的异步视图接口：保留。** 比不经代理的异步视图每次多 0.7 ns，比同步接口的命中还快。
- **声明的挂起视图接口：代理每次命中多 10.3 ns，是挂起视图本身的 2.9 倍，也是同步接口代理（2.5 ns）的 4 倍，超过约 2 倍的门槛。** 它不分配（0 B/op），所以成本在转发这一步的 CPU 上；走同一个 `ViewHandler` 的异步接口只多 0.7 ns。按维护者的安排，优化另开切片，本 PR 不改代码。

## 后续：声明的挂起视图接口的代理（2026-11-05）

“补测”测得声明的挂起视图接口的代理每次命中多 10.3 ns。这一节查清原因并给出修复与对比。

**原因是 C2 的内联深度上限，不是反射。** 以 `-XX:CompileCommand=PrintInlining,*_jmhStub` 查看 `l2HitViaSuspendingInterface` 的编译：
- `Method.invoke` 被一路内联到视图：代理的 `Method` 是代理类的 `static final` 字段，`DirectMethodHandleAccessor` 的方法句柄因此折叠为常量，这也是 0 B/op 的原因。
- 转发多出 6 个计入深度的帧（代理方法、`ViewHandler.invoke`、`forward`、`Method.invoke`、`DirectMethodHandleAccessor.invoke`、`invokeImpl`）与 3 个 LambdaForm 帧。挂起调用经协程的启动进入代理，又多 5 帧（`wrapWithContinuationImpl`、函数引用的两个 `invoke`、`access$suspendingInterfaceGet`、`suspendingInterfaceGet`）。`BoundedLocalCache.getIfPresent` 之下的 `ConcurrentHashMap.get`、`hasExpired`、`afterRead` 等因此都标为 “inlining too deep”（`MaxInlineLevel` 默认 15），变成真正的调用。
- 异步接口没有协程的这 5 帧，而且这次它的代理方法单独编译（“already compiled into a big method”），同一条转发只多 0.7 ns。
- 验证：同一个 jar 以 `-XX:MaxInlineLevel=25` 运行，挂起接口从 15.87 ns 降到 6.26 ns，直接调用挂起视图是 5.22 ns。10.6 ns 中约 9.6 ns 来自内联深度，反射本身约 1 ns。

**试过的转发方式**（诊断用的 JMH：同一个 jar 中的临时变体，以系统属性切换，未提交；1 线程，avgt，2 fork × 3 × 3 s，持本机锁）：

| 转发方式 | ns/op | 比直接调用多 | `gc.alloc.rate.norm` |
|------|------:|------:|------:|
| 直接调用 `suspending().get` | 5.22 | – | 0 B |
| `Method.invoke`（修复前） | 15.87 | 10.6 | 0 B |
| `Method.invoke`，`-XX:MaxInlineLevel=25` | 6.26 | 1.0 | 未测 |
| Kotlin 函数引用（转为 `Function3` 调用） | 8.01 | 2.8 | 未测 |
| Java 静态方法直接调用 `view.get(key, continuation)` | 7.14 | 1.9 | 40 B |
| `LambdaMetafactory` 生成的调用桩 | 7.21 | 2.0 | 未测 |
| 绑定到视图的方法句柄（实例字段） | 6.76 | 1.5 | 16 B |

- 直接调用（函数引用、Java、`LambdaMetafactory`）让视图被内联进 `ViewHandler.invoke` 单独的编译结果。它因此超过 `InlineSmallCode`，调用方不再内联它，代理的参数数组逃逸（Java 版 40 B/op）。
- 实例字段中的方法句柄不是编译期常量，C2 总是在外调用它（“receiver not constant”）。视图的命中路径编译在自己的方法里，有完整的内联预算，与调用方的深度无关；`ViewHandler.invoke` 的编译结果保持很小，仍内联进代理方法，参数数组被标量替换。剩下的 16 B/op 是基准自己的协程包装逃逸进句柄调用：`startCoroutineUninterceptedOrReturn` 对函数引用创建一个 `RestrictedContinuationImpl`，真实的调用方传入的是已有的状态机。

**修复**（`CacheProxies.ReadHandles`）：挂起视图中 L2 命中可以直接返回的读取（`get`、带 loader 的 `get`、`getAll`、`lookup`、`lookupAll`、`getVersioned`）经创建代理时绑定到视图的方法句柄调用。其余方法（包括全部写入）仍经 `Method.invoke`：写入总要访问 L1，这几 ns 可以忽略。异步视图不变。第一版的异常路径把参数数组传给不内联的 `rethrow`。C2 的逃逸分析不区分路径，数组因此每次都要分配（40 B/op，7.95 ns）；改为只传最后一个参数之后回到 16 B/op。

**对比**（`scripts/jmh-compare.sh -b l2HitViaSuspendingInterface,l2HitSuspending,l2HitViaInterface,l2HitViaAsyncInterface,l2HitMixed -t 1,8 -r 3`，预热 2 × 2 s，测量 3 × 3 s，持本机锁；基线 `origin/main` 的 844b0f88，新侧是修复后的提交；2026-11-05 02:07–02:23，机器与 JVM 同上，Redis 是 `cocache-redis` 容器）。60 次运行全部有效，没有格子的中位数落在 −2% 到 −4% 之间，不复测：
